# AX1 StockFlow Backend Independent Audit

**Audit date** 19 November 2026 (Asia/Kolkata)  
**Reviewer** AX1  
**Final recommendation** FAIL

StockFlow passed all 49 supplied tests on PostgreSQL 18.6 and served the expected health and dashboard results. Independent checks found two ways to leave an active product/store pair without an inventory balance. They also found that a CSV preview can approve a malformed or unpersistable row, and that two valid store creations can block unrelated CSV imports. These defects affect ordinary inventory workflows in the local MVP. Authentication and authorisation are explicitly deferred, so the tested application remains suitable only for a trusted demonstration environment.

## Scope and verification

Reviewed the backend application, all four migrations, the supplied tests, architecture and API documentation, and the frontend API call sites relevant to the integration and retry claims. The workspace had no accessible Git metadata. No source code, dependencies, configuration files, or existing databases were changed. Runtime writes were confined to a new disposable PostgreSQL cluster in the Windows temporary directory, bound to `127.0.0.1:55491`. The application used that database exclusively during verification. Both audit processes were stopped. The execution policy denied recursive cleanup, so the stopped cluster files remain in `%TEMP%/stockflow-ax1-4dba6930e25641888f86aeccce58baa3`.

Commands ran from `backend/` using its existing Python 3.15.2 virtual environment. Pytest's cache and Python bytecode output were disabled. The comparison URL identified an unused database name on the same disposable cluster. The suite itself migrated and reseeded the dedicated test database according to its fixture.

## Conclusion

1. **Architecture assessment.** Routes, schemas, services, repositories, models, settings and migration code have identifiable responsibilities. Services own write transactions. Import and dashboard query SQLAlchemy directly, and import combines parsing, reference resolution, idempotency and persistence in one module. Dependency pins and the supplied lock are present, and the environment passed `pip check`.
2. **Database integrity assessment.** Primary keys, unique SKU/store indexes, the unique balance pair, foreign keys, nonnegative checks and movement arithmetic provide strong per-row integrity. Balance coverage for active pairs breaks across concurrent creation and reactivation. A clean migration reaches head, with three server-default differences outside the configured Alembic comparison.
3. **Transaction and concurrency assessment.** Movements lock a specific balance with `FOR UPDATE`, calculate against the locked quantity and commit the balance, movement and activity together. Supplied PostgreSQL tests demonstrated oversell prevention and rollbacks. Imports lock refreshed balances in product/store order and commit with activity. Coordination with product/store lifecycle operations remains incomplete.
4. **Idempotency assessment.** Each operation family reserves its primary-key-backed key with PostgreSQL `ON CONFLICT DO NOTHING`. A competing request waits for the insert outcome. After a successful transaction it can verify the hash and replay the stored movement or CSV result. When a transaction aborts the reservation and stock change roll back together. Same-key conflicts return `409`. Movement contention passed the supplied test, and the independent CSV contention probe returned equal results with one activity write. Cross-reload retry continuity remains a client gap.
5. **CSV processing assessment.** UTF-8/BOM handling, canonical headers, store-name/code and SKU resolution, duplicate-pair detection, rejected-row reporting, preview separation and transactional all-or-nothing commit are implemented. The dict index costs linear time to build over the catalogue with average constant-time row lookups. Input bounds, strict quoting, ambiguous references and buffering need correction.
6. **API assessment.** The documented surface is registered and the live success checks matched seed data. The public SKU endpoint uses a normalised indexed equality query. Replenishment uses `heapq` with largest deficit, then higher threshold, case-folded SKU/store code and numeric IDs as tie-breakers. Full heap construction and draining cost `O(n log n)` time and `O(n)` space. Typical filtering, pagination and status codes are coherent. OpenAPI, path validation and upload contracts need alignment.
7. **Security assessment.** Reviewed application query paths use bound SQLAlchemy expressions and fixed SQL where text is used. CSV names are display metadata and the upload path does not write to the filesystem, so no file path traversal was found. Environment-based settings and local CORS support a demo. Authentication, authorisation and tenant isolation are absent. Test-target attestation, upload limits, log redaction and readiness checks warrant work before broader use.
8. **Test coverage assessment.** All 49 supplied tests ran successfully against isolated PostgreSQL. The strongest coverage is movement arithmetic, real lock contention, failure rollback and replay. Lifecycle, validation boundaries, cross-workflow ordering, and integration cases listed in AX1-019 and AX1-020 remain open.
9. **Prioritised remediation.** First fix and reconcile active pair provisioning across create and reactivation, and add PostgreSQL regression tests. Next align CSV and movement bounds with database storage, reject malformed CSV, fix store reference ambiguity and cap streaming uploads. Then harden isolation and schema checks, settle snapshot and retry semantics, and align the API contract. Before any wider deployment, implement access control and actor attribution.
10. **Final recommendation — FAIL.** The independently reproduced balance lifecycle failures prevent acceptance of the completed multi-store inventory implementation. Reassess after the active pair and CSV correctness fixes have passing regression coverage. Keep any interim use within the trusted demo scope.
